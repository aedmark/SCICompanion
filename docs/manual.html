Product foundations

What SCI Companion is, what it operates on, and the compatibility boundary readers should assume.

SCI Companion overview

#
overviewuser-facing

A Windows IDE for creating and maintaining Sierra Creative Interpreter games.

What it does

  1. Provides one desktop workspace for scripts, pictures, views, fonts, audio, messages, vocabularies, and other SCI resources.
  2. Targets game projects from SCI0 through SCI1.1 as the documented support range.

How it works

  1. Runs as a native MFC multiple-document application built from SCICompanion.sln.
  2. Routes most product behavior through SCICompanionLib, with resource-specific documents, views, dialogs, compiler code, and storage code.

Why it works this way

Recorded in D-001: the established Windows/MFC architecture and thin-executable/shared-library split are the system to maintain unless the maintainer explicitly directs a broader rewrite.

Game projects and resources

#
datacompatibilitysafety

A game project is user-owned source and resource data, not merely an IDE workspace file.

What it does

  1. Opens an SCI game directory and exposes its scripts and encoded resources through specialized editors.
  2. Can write compiled scripts, patch files, resource maps or volumes, exports, and other project artifacts.

How it works

  1. Version and storage detection select resource sources and format-specific readers or writers.
  2. ResourceMap, resource entities, and MFC documents carry loaded data into editors and back to storage.

Why it works this way

Inferred from the resource architecture and test fixtures: SCI generations and storage layouts differ enough that version-aware handling must be central, and user projects must be treated as valuable mutable data.

Compatibility scope

#
SCI0SCI1.1Wine

The documented product range is SCI0 through SCI1.1; narrower claims need direct evidence.

What it does

  1. Supports the formats and workflows needed for documented SCI0 through SCI1.1 game projects.
  2. Includes recent compatibility fixes for running file dialogs under Wine, without claiming a complete Wine support matrix.

How it works

  1. SCI version traits and format-specific implementations branch parsing, rendering, compilation, and writing behavior.
  2. Unit fixtures cover representative variants; manual checks cover workflows that native tests do not exercise.

Why it works this way

The SCI family is not one uniform format. The support statement follows the root README; architecture notes explicitly avoid turning the presence of SCI2 picture fixtures into a claim of full SCI2 support.

Application shell

#
MFCstartupUI

The SCICompanion project starts MFC, restores preferences, and wires document templates to frames and views.

What it does

  1. Creates the desktop process, main frame, editor document templates, recent-file behavior, and application preferences.
  2. Provides the Windows resources and shipped files that surround the reusable library.

How it works

  1. SCICompanionApp::InitInstance() initializes app state and OLE, selects the mtnPhilms registry profile, loads settings, and registers MFC document templates.
  2. Each document template connects a resource document class to its frame and view classes.

Why it works this way

Recorded in D-001: the executable stays thin so reusable editor, resource, and compiler behavior remains concentrated in SCICompanionLib.

Shared application library

#
C++static librarycore

SCICompanionLib owns most domain behavior and editor implementation.

What it does

Supplies resource storage, compiler/decompiler logic, documents, views, frames, dialogs, utilities, media handling, and shared application state to the executable and tests.

How it works

  1. Builds as a static MFC library referenced by both the executable and native test projects.
  2. Organizes major areas beneath SCICompanionLib/Src/, with AppState coordinating cross-cutting application services.

Why it works this way

Recorded in D-001 and reinforced by the existing project graph: keeping behavior in a shared library lets the shell and tests use the same implementations while preserving the established MFC design.

Resource system

#
resourcesstorageformats

Version-aware loaders and writers translate SCI storage into editable resource entities.

What it does

  1. Enumerates, loads, creates, deletes, and saves typed SCI resources.
  2. Hides resource-map, volume, patch-file, and version-specific details from higher editor layers where possible.

How it works

  1. Resource sources feed blobs and metadata into ResourceMap and resource-specific entity decoders.
  2. Documents and tools modify entities, then encoders and selected resource sources persist the result.

Why it works this way

Inferred from the component boundaries and tests: centralizing storage/version decisions reduces the chance that each editor implements incompatible file handling and helps protect unrelated game resources during a save.

Evidence
  • Resource source tree SCICompanionLib/Src/Resources/

MFC document, frame, and view classes implement resource-specific editing experiences.

Edit, save, and reload a resource

#
editingpersistencerecovery

Resource changes move through an editor document into version-aware persistent storage.

What it does

Lets a user change a resource, save it into a disposable or backed-up game project, close it, and reopen it with the change preserved.

How it works

  1. A resource document owns the editable entity and notifies its view as commands mutate state.
  2. Saving encodes the entity for the active SCI version and commits it through the selected resource source; reloading exercises the reader path again.

Why it works this way

Inferred from user-data risk and the test strategy: save/reload is the meaningful persistence contract, while checking only an in-memory editor state would miss writer and compatibility failures.

Compile and run a game

#
compilelaunchprofiles

Script compilation updates game resources; run profiles launch the selected interpreter or emulator.

What it does

  1. Compiles changed scripts and reports errors for navigation and correction.
  2. Launches a configured game executable or interpreter with its stored parameters.

How it works

  1. Compiler code parses source and headers, resolves symbols and classes, then generates script resources for the active game.
  2. RunLogic stores executable profiles and launches the chosen program using the configured path and arguments.

Why it works this way

Inferred from the IDE workflow: compilation and launch are connected so authors can move quickly from source changes to a game run, while explicit profiles accommodate different interpreters and local installations.

Build environment

#
buildVisual StudioWindows

The native solution requires Windows, Visual Studio C++/MFC, and a compatible Windows SDK.

What it does

Builds the Prof-UIS dependency, shared library, executable, and unit-test DLL for the selected solution configuration.

How it works

  1. Run msbuild SCICompanion.sln /m /p:Configuration=Release /p:Platform=Win32 from a compatible Visual Studio Developer Command Prompt.

Verification strategy

#
testsevidencemanual checks

Documentation checks run everywhere; native tests and workflow checks require a Windows-capable environment.

What it does

  1. Checks documentation references and the 3x manual source on any system with Python 3.
  2. Uses a Visual Studio native test DLL for covered logic and manual smoke tests for editor workflows and compatibility.

How it works

  1. tools/check_docs.py validates repository-memory documents; tools/3x_manual.py check validates triads, evidence presence, and related IDs.
  2. vstest.console.exe Release\UnitTests.dll runs the discovered native tests after a successful build; release checks use disposable SCI0 and SCI1.1 projects.

Why it works this way

Recorded in the testing guide: each check should state both what it proves and what it cannot, because a generated document pass does not prove C++ behavior and native unit tests do not prove complete UI or format compatibility.

Preferences and local state

#
registrypreferenceslocal state

Registry-backed settings remember editor preferences, paths, recent files, and run profiles on the local machine.

What it does

Persists application and dialog choices between sessions and offers a startup reset path when settings become invalid.

How it works

  1. MFC profile APIs read and write beneath the mtnPhilms application registry key.
  2. Holding Shift during startup follows the current reset path; persistent dialogs separately retain their last folder.

Why it works this way

Inferred from desktop usability and current implementation: local persistence avoids repeated configuration, while an explicit reset path provides recovery from stale or incompatible settings.

Security and data-safety boundaries

#
securityinput validationrecovery

Game data, imported media, paths, registry values, and process arguments are untrusted inputs.

What it does

Protects user projects and the host machine from malformed resources, unsafe process launch, accidental overwrite, and disclosure of private paths or assets.

How it works

  1. Format handlers validate counts, offsets, sizes, and encodings; contributors add negative cases at changed boundaries.
  2. Tests use committed fixtures or disposable copies, process launch preserves argument boundaries, and reports are sanitized before sharing.

Why it works this way

Recorded in the security and agent guidance: SCI Companion crosses file-format, filesystem, registry, and process boundaries while operating on valuable user-owned projects, so safe failure and recoverability are part of correctness.
